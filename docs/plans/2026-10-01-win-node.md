**Goal.** `ph node` runs on a Windows 10/11 PC (x64, MSVC), started by hand
from an elevated (Administrator) console with a config file, exactly the way
`sudo ph node -c x.toml` is run on Linux. It creates a Wintun interface,
addresses it, accepts docking adapters, forwards their traffic, and reaches
the visa service through its own TUN. The adapters and the visa service stay
on Linux. Behaviour is the same as on Linux; throughput is not.

**Not the goal** (see *Out of scope*): a multi-homed or wildcard-bound node,
a Windows service or installer, an automated Windows integration tier,
node-to-node links, node and adapter on the same Windows host.

## Background — what the adapter port left for the node

The Windows adapter port (umbrella [zipline#126](https://github.com/mkolehmainen/zipline/issues/126),
decisions retired into `docs/SYSTEM_OVERVIEW.md` and `docs/BUILD.md`
"Design decisions") made `ph` build and run on Windows: Wintun behind
`ZprTun`/`TunCtl`, the `WaitSet`, the `windows_unbatched` batch_io engine,
`netsh` for addresses and routes, a named-pipe control channel, console
events for signals. `ph node` is the same binary and compiles, but it was
declared unsupported (D1) and has never been run. Inventory taken by reading
the code at the commits above; nothing was executed.

### 1. What the node does that the adapter does not

All paths under `zl-zpr-core/adapter/ph/src/` unless shown in full.

| Where | What |
|---|---|
| `main_args.rs:179`, `main_argparse.rs:88-112`, `config.rs:469-479` | `Command::Node`, `PhMode::Node`, `Config::new_for_node`; a node requires `zpr_addr`, `certificate_file` and a Noise private key. |
| `main.rs:403-559` | Opens `fastpath_concurrency` substrate sockets on `self_addr` (default `0.0.0.0:0`, port forced to 5000 at `:386`). Unix: pktinfo (`:421`) and `SO_REUSEPORT` (`:425`). Windows: one socket, `windows_substrate_bind_check` (`:536`, `batch_io.rs:1492`) rejects a wildcard bind. |
| `main.rs:596-653` | Advertised substrate address: `advertised_substrate_addr`, else a concrete `self_addr`, else startup fails. Platform-neutral. |
| `main.rs:731-784`, `assembly.rs:324` | Internal link pair, ZDPR workers, local actor addresses, then `local_zpr_addrs_missing_from_tun`: **refuses to start if the node's ZPR address is not on the TUN**, printing an `ip -6 addr add` hint. |
| `main.rs:916-952`, `libnode2/src/vss.rs:72` | VSS listener binds `zpr_addr[0]:8183`; VSConn connects to `[fd5a:5052::1]:5002` through the TUN. Pure tokio TCP + rustls + capnp, no `cfg`. |
| `fastpath.rs:382+`, `mgmt/node.rs`, `address_pool`, `adapter_manager_worker`, `visa_mgmt` | Forwarding, next hop, visa tables, address pool. **No `cfg` anywhere**; the unit tests compile and pass on Windows (verified by the adapter port's hand-run `cargo test`; the CI job that would run them is inert, see N5). |
| `link_state.rs:347` | `NodeToNode` links are unsupported on every platform. |

### 2. Who addresses the node's TUN today

Nobody in `ph`. Only adapter activation calls `TunCtl::add_address` and
`add_route` (`link_state.rs:1585-1673`).

- **Linux**: an address cannot be set at TUN creation; the integration
  scripts add it out of band with `ip addr add NODE peer VS dev tun0`
  (`integration-test/lib/common_funcs.sh:147`). The `peer` form makes the
  visa service address on-link.
- **macOS**: the address is applied at utun creation only when `tun_if` is
  unset (`main.rs:309-322`); with `tun_if` set, `new_mq` fails with
  "address is required on macos" (`sys/macos/zprtun.rs:49`). A macOS node has
  never been run either.
- **Windows**: `new_mq` ignores its `_address` argument
  (`sys/windows/zprtun.rs:78-81`) and deletes any adapter of the same name
  from a previous run (`:95-113`), so a pre-configured address cannot
  survive. `has_address` (netsh, `:215`) returns false and `main.rs:766`
  exits. The VSS bind at `:919` would fail for the same reason. **Every
  Windows node fails to start today.**

### 3. Windows UDP "connection reset"

On Windows, after a `sendto` to a peer that answers with ICMP port
unreachable, the next `recvfrom` on an unconnected UDP socket fails with
`WSAECONNRESET` (10054) unless `SIO_UDP_CONNRESET` is disabled. Nothing in
the crate mentions either. `windows_unbatched::recv_from_batch`
(`batch_io.rs:1621-1691`) returns the error for the first datagram of the
batch, `fastpath_io.rs:124-128` wraps only `WouldBlock`, and the
`.expect("unrecoverable substrate socket error")` panics the fastpath
thread. An adapter talks to one node; a node talks to many adapters, any of
which can exit, so a node hits this routinely.

### 4. Already portable, no work

Forwarding and visa logic (§1), libnode VSConn and VSS, the named-pipe
control channel (`sys/windows/control.rs`), console-event signals
(`signal_worker.rs:54`), Wintun create/teardown, the single-worker datapath
(`config.rs:94-101`; Wintun `new_mq` enforces one queue,
`sys/windows/zprtun.rs:83`), packet steering degrading to a warning
(`main.rs:580-588`). Capture is Unsupported on Windows in both modes
([zipline#148](https://github.com/mkolehmainen/zipline/issues/148)).

### 5. Tests and CI

`.github/workflows/adapter.yml` would build `ph` and run its unit tests on
ubuntu, macos and windows (`:48-72`, `:107-114`), including node-mode
assembly and `vss_worker` tests, but **Actions is disabled on the forks**, so
nothing runs; the local gate (N5) is the only gate. Every integration job is
`ubuntu-latest` only. `integration-test/windows-adapter-test.md` is
the hand-run end-to-end test; in it the node is on Linux (`:270-276`) and
only the adapter is on Windows. **No test anywhere runs a node on Windows or
macOS.** The Linux scripts run the node multi-homed (four veths plus
`C_ALT`, `one-node-test.sh:27-31`) with a wildcard bind, a shape the Windows
engine rejects by design (D5).

## Decisions

**N1. A dev/demo node: single-homed, concrete `self_addr`, elevated console,
single worker.** Adapters and the visa service run on Linux. A Windows node
must be given a concrete `self_addr` (or `advertised_substrate_addr`); the
wildcard-bind rejection from D5 stands and
[zipline#150](https://github.com/mkolehmainen/zipline/issues/150) keeps
multi-homing. No service wrapper
([zipline#147](https://github.com/mkolehmainen/zipline/issues/147)).
Functional parity with Linux is the bar; throughput through one unbatched
socket is measured in C3 and recorded, not fixed.

**N2. Nothing may assume `ph` is the only instance on the host.** A later
phase will run a node and an adapter on one Windows machine (peer-to-peer,
possibly over loopback or an in-process channel). So: the dock listen must
work with a loopback `self_addr`; `tun_if` stays per-instance and nothing
hardcodes a Wintun adapter name; no change may add a host-wide singleton
(fixed pipe name, fixed port, fixed route ownership). Known pre-existing
collision, recorded here and **not** fixed in this plan: the control path is
derived from the owner uid alone (`config.rs:356`,
`admin_api::control_socket_path`), so a node and an adapter for the same user
already collide on every platform unless `--control-path` is given. Z1 files
this as a deferred issue for the peer-to-peer work.

**N3. The node applies its own ZPR address through `TunCtl`, on every
platform.** Before the `local_zpr_addrs_missing_from_tun` check at
`main.rs:766`, for each local ZPR address: if `has_address` is false, call
`add_address(addr, ZPRNET_PREFIX_LEN)`; then make the visa service address
reachable through the TUN (on Linux the existing `peer` form, or a /128
route via the TUN, already does; on Windows `netsh add address` ignores the
prefix, so an explicit `add_route` for `fd5a:5052::1/128` — or the
`ZPR_INTERNAL_NETWORK/ZPRNET_PREFIX_LEN` on-link route — is required). The
existing check still runs afterwards and remains the hard stop. This is
idempotent, so hand-configured Linux setups and the integration scripts'
`ip addr add` are untouched; the only Linux behaviour that changes is the
branch that today exits with an error. Rejected: a Windows-only arm
(the macOS plan would redo it and the two drift); removing the out-of-band
`ip addr add` from the Linux scripts in this plan (unrelated churn; the
scripts may drop it once C1 lands).

**N4. The Windows substrate socket tolerates connection reset.** At bind,
disable `SIO_UDP_CONNRESET` via `WSAIoctl` (one call in the `cfg(windows)`
block at `main.rs:533-538`). Belt and braces: `windows_unbatched::
recv_from_batch` treats `ErrorKind::ConnectionReset` as "no datagram" and
continues the batch, and `fastpath_io.rs:124` keeps its `expect` for
everything else. Applies to the adapter as well. In the same task, the
`.expect("substrate socket configuration unusable on Windows")` at
`main.rs:537` becomes a logged startup error with `ExitCode::FAILURE`, like
the address check at `:766`, so a misconfigured node fails cleanly with the
message that already names the fix.

**N5. Verification is a hand-run test document plus unit tests; no new CI
tier.** `integration-test/windows-node-test.md` mirrors
`windows-adapter-test.md` with the roles inverted: the Windows VM is the
node (concrete `self_addr`, `advertised_substrate_addr` = the VM's LAN
address); the Linux host runs valkey, the visa service and its adapter, and
one client adapter in netns; traffic flows end to end. The unknowns the code
reading could not settle are its checklist (C3). Unit tests for N3 and N4
run on Linux and macOS where the logic is portable, and on a Windows box for
the `cfg(windows)` parts, through the core gate below. Automation is
[zipline#152](https://github.com/mkolehmainen/zipline/issues/152) and is
unchanged by this plan.

**N6. Docs closure retires D1's "nodes stay on Linux".** `SETUP.md`
"Windows" documents the node role and its constraints (concrete
`self_addr`, firewall rules, single-homed); `docs/SYSTEM_OVERVIEW.md`
"Design decisions" gets these N-decisions and loses the "unsupported and
untested" sentence; this plan is retired per `skills/zpr/SKILL.md`.

**Build gate used by every task below.** `zl-zpr-core` has no root
`make check` and the forks have no CI (Actions is disabled on all of them,
by decision — see `docs/BUILD.md` and `skills/zpr/SKILL.md`), so "CI green"
is never an acceptance criterion. The **core gate** is BUILD.md's CI
equivalent, run locally from the workspace root on the OS named, with the
transcript quoted in the PR:

```bash
cargo fmt --check
cargo build --all-targets --config 'build.rustflags = ["-D", "warnings"]'
make test
```

On a Windows box the same three commands, with `ph-cli` built and tested
`--no-default-features` (no `pcap`); from Linux,
`cargo xwin check -p ph --target x86_64-pc-windows-msvc` is the cheap
pre-check but does not compile test code and does not replace the Windows
run.

## Tasks

### C1 — [zipline#159](https://github.com/mkolehmainen/zipline/issues/159): node applies its own ZPR address and visa-service route through `TunCtl` (`zl-zpr-core`, all platforms)

**Blocked by:** none.

Implement N3. In `main.rs` node branch, immediately before the
`local_zpr_addrs_missing_from_tun` check (`:731-784`): for each address in
`config.zpr_addr`, `if !tun_ctl.has_address(addr)? { tun_ctl.add_address(addr,
ZPRNET_PREFIX_LEN)? }`; then ensure the visa service address is reachable via
the TUN using `add_route` where `has_address` alone does not make it on-link.
Put this in one helper on `Assembly` (next to
`local_zpr_addrs_missing_from_tun`, `assembly.rs:324`) so it is unit-testable
with a mock `TunCtl`, and so the macOS plan calls the same code. Failure of
`add_address` logs the platform's manual command (the hint that already
exists at `main.rs:758-761`) and exits `FAILURE`. On Windows, `sys/windows/
zprtun.rs::add_address` ignores `prefix_len`; document that the on-link
reachability of `fd5a:5052::1` therefore comes from the route, not the
address, and extend `add_route` if a /128 host route needs different `netsh`
arguments.

Respect N2: no change to adapter activation, no new global state.

**Tests.** Unit test on the helper with a mock `TunCtl`: address absent →
`add_address` called once with `ZPRNET_PREFIX_LEN`; address present →
not called (idempotent); `add_address` error → helper returns the error. The
Linux integration scripts are unchanged and stay green (their out-of-band
`ip addr add` now runs against an address the node would have added anyway;
the scripts add it first, so `has_address` is true and nothing is called).

**Acceptance.** Core gate clean on Linux and macOS. Netns tier green
(`zpr-dev build --test netns`), quoted in the PR. On a Linux host, `ph node`
started **without** the out-of-band `ip addr add` reaches the visa service
(a hand check, stated in the PR). Touches the TUN setup path, not the
datapath; the gate escalation in `skills/zpr/SKILL.md` does not apply.

### C2 — [zipline#160](https://github.com/mkolehmainen/zipline/issues/160): Windows substrate socket tolerates `WSAECONNRESET`; wildcard bind fails cleanly (`zl-zpr-core`, Windows)

**Blocked by:** none.

Implement N4.

1. In the `cfg(windows)` block at `main.rs:533-538`, after the bind check,
   call `WSAIoctl(SIO_UDP_CONNRESET, FALSE)` on the raw socket (via the
   `windows-sys` crate already in the tree; no new dependency). Comment why.
2. In `windows_unbatched::recv_from_batch` (`batch_io.rs:1621-1691`), map
   `ErrorKind::ConnectionReset` to "stop this batch, return what was
   received", the same way `WouldBlock` is handled, with a `trace!` counter
   so a storm is visible. This is the fallback if the ioctl is ever absent.
3. Replace the `.expect` at `main.rs:537` with `error!(target: STARTUP, ..)`
   and `return ExitCode::FAILURE`, reusing the message already produced by
   `windows_substrate_bind_check`.

**Tests.** `windows_substrate_bind_check` already has a unit test for the
message; add one that a loopback and a concrete LAN address both pass (N2:
loopback must stay valid). The `ConnectionReset` mapping in
`recv_from_batch` gets a unit test behind `cfg(windows)` using a bound UDP
socket that sends to a closed local port and then receives; it runs in the
Windows core-gate run. Unix engines are untouched.

**Acceptance.** Core gate clean on Linux and macOS, and on a Windows box
(transcript quoted). A hand check on the same Windows box: start `ph
adapter` against a node address nothing listens on, observe it does not
panic (covers the adapter side of the same bug). Datapath change on the
Windows engine only; the netns tier is still run and quoted.
