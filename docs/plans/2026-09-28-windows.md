# FEATURE: Windows compatibility for `ph adapter`

**Status:** IN FLIGHT — umbrella: *to be filed* (zipline). No blockers outside this plan.
**Date:** 2026-09-28
**Repo state this plan was written against:** `zl-zpr-core` @ `25f9e93`, `zl-zpr-utils` @ `8be1f93`, `zl-zpr-dev-tools` @ `8804b10`, `zl-zpr-dev-context` @ `0437982`, all on `zipline`. Line references are against those commits.

---

**Goal.** `ph adapter` runs on an end-user Windows 10/11 PC, started by hand
from an elevated (Administrator) console with a config file, exactly the way
`sudo ph adapter -c x.toml` is run today. It creates a Wintun interface, docks
to a Linux node, and carries the user's own traffic. `ph-cli` talks to it over
a named pipe. Nodes stay on Linux.

**Not the goal** (see *Out of scope*): a Windows service or installer, packet
capture to a file on Windows, `ph node` on Windows, Windows CI for the
integration tier.

---

## Background — what is platform-specific today

`ph` is 35k lines. Almost all of it is portable. The platform-specific code
falls into four groups, listed here from cheapest to most expensive to port.
Inventory taken at the commits above; `git grep` for the symbols named if a
line has moved.

### 1. The existing platform seam: `adapter/ph/src/sys/`

There is already a per-OS layer, and it is the model for Windows.

| File | What it does |
|---|---|
| `sys/mod.rs:1-13` | `#[cfg(target_os)]` selects `linux` or `macos`; re-exports `ZprTun` and `TunPiImpl`; generic `TunPi` (per-packet header) with `PI_SIZE`. |
| `sys/linux/zprtun.rs` | TUN via `tokio-tun`, multi-queue. Addresses and routes by running `/usr/sbin/ip`. |
| `sys/macos/tun.rs`, `sys/macos/zprtun.rs` | Raw `utun` via `PF_SYSTEM` socket and ioctls; addresses and routes by running `/sbin/ifconfig` and `/sbin/route`. One queue. |
| `sys/linux_route.rs`, `sys/macos_route.rs` | Pure parsers for `ip -6 route show` and `route -n get`. **Compiled on every OS** so their tests run on Linux. `Platform` enum at `linux_route.rs:36` has `Linux` and `MacOs`. |
| `sys/posix/notify.rs` | `Notify`: a non-blocking `pipe()` used as a wakeup fd that `poll()` can watch. `post()`, `consume()`, `poll_fd()`. **Unix-only but not `cfg`-gated.** |
| `tun_ctl.rs` | `TunCtl` trait: `set_carrier`, `add_address`, `clear_address`, `has_address`, `add_route`, `route_owner_conflict`. The interface a Windows TUN must implement. |
| `zprtun.rs` | `TUN_HAS_PI = PI_SIZE > 0` already allows for a header-less TUN, which is what Wintun is. |

The macOS port followed one pattern: OS code goes in `sys/<os>/` behind `ZprTun`
and `TunCtl`; behavioural differences are small `#[cfg]` blocks in `main.rs`,
`config.rs`, `fastpath_io.rs` and `packet_steering.rs`; pure parsers stay
portable so their tests run everywhere. Windows follows the same pattern.

### 2. What macOS could reuse and Windows cannot: POSIX fds

macOS reused the POSIX pieces wholesale: `poll(2)`, pipes, AF_UNIX sockets,
the `posix_unbatched` batch_io engine. Windows has none of these in the form
the code uses them. This is the main new cost.

- **The fastpath wait.** `fastpath_worker.rs:74` calls `nix::poll::poll` over
  five fds: the substrate UDP socket, the TUN, and three `Notify` pipes
  (requeue, mgmt, returns). `fastpath_io.rs:10,67-83` exposes them as
  `BorrowedFd`. `packet_queue.rs:268-270` and `two_way_queue.rs:364-366` wait on
  `Notify` fds the same way. Wintun hands the caller a HANDLE and a ring buffer,
  not an fd, so nothing here can be reused as-is.
- **batch_io** (`batch_io.rs`, 2033 lines). The `BatchIoImpl` trait
  (lines 70-114) is typed on `BorrowedFd` and `libc::c_int` flags. Engines:
  `io_uring` (Linux only, ~860 lines, already gated) and `posix_unbatched`
  (lines 1126-1400: `read`/`write` on the TUN fd, `sendmsg`/`recvmsg` with
  `IP_PKTINFO` control messages on the socket).
- **Substrate socket setup** (`main.rs:430-530`): `set_reuse_port` at 443 and
  500 (socket2 exposes this on unix only; Windows has no `SO_REUSEPORT`),
  disconnect-by-`AF_UNSPEC` at 509, Linux-only temp socket. Worker
  concurrency defaults to 4, or 1 on macOS (`config.rs:92-95`); Windows needs 1
  for the same reason. `packet_steering.rs` already has a `not(linux)` arm that
  returns Unsupported; `fastpath_io.rs:357-365` already falls back for
  `MSG_CONFIRM`.

### 3. IPC, paths and permissions

- **Control socket** (Cap'n Proto RPC, ph-cli to ph): `tokio::net::UnixListener`
  at `main.rs:270-279`, `admin_worker.rs:99`; client `UnixStream::connect` at
  `adapter/cli/src/main.rs:217`.
- **Capture socket**: a second `UnixListener` (`main.rs:306-323`,
  `set_capture_file_worker.rs`). ph-cli opens the pcap file and passes the
  **fd over SCM_RIGHTS** (`adapter/cli/src/main.rs:895-930`,
  `admin_worker.rs:732-743`), so `ph`, which runs as root, never writes to a
  path a user chose. The `capnp-ancillary` feature is the same thing via
  `capnp-futures/tokio-unix-fd-stream`.
- **Internal capture queue**: `packet_buffer_socket_pair` (`main.rs:101-118`)
  is an AF_UNIX `SOCK_DGRAM` socketpair feeding `capture_worker.rs`; sender in
  `queues.rs:150-200` checks `ENOBUFS`. Windows AF_UNIX has neither datagram
  sockets nor `socketpair`. Commit 726be13 already replaced the *other*
  datagram-socket queues with in-house queues; this one was left.
- **Paths and ownership**: `/var/run/zpr/<uid>/{control,capture}.sock`
  (`admin-api/src/socket_owner.rs:76-106`), `$XDG_DATA_HOME` fallback
  (`admin-api/src/data_home.rs`), owner from `SUDO_UID`/`SUDO_GID`/`PKEXEC_UID`
  (`socket_owner.rs:46-65`). `config.rs:355-415` (`prepare_socket_dirs`) and
  `socket_access.rs` (286 lines) do `chown`, mode `0o700`/`0o600`/`0o660`, and
  passwd/group lookups via `nix`. `admin-api/src/socket_owner.rs:111` probes
  liveness with `std::os::unix::net::UnixStream`.
- **Signals**: `signal_worker.rs` uses `tokio::signal::unix` for SIGINT
  (graceful, second one hard-exits), SIGTERM (graceful), SIGUSR1 (print
  counters).
- **ph-cli**: `geteuid` at `main_args.rs:40` (picks the per-uid socket path)
  and `oidc.rs:771` (root may not open a browser); browser launcher is `open`
  on macOS else `xdg-open` (`oidc.rs:789-797`); `pcap` is a default feature
  used only to compile a filter string (`main.rs:604-607`) and would need the
  Npcap SDK on Windows.

### 4. Dependencies

- **`zpr-ext`** (`zl-zpr-utils/zpr-ext`, tag `zpr-ext-v0.5.3`) **does not
  compile on Windows**, independent of anything in core:
  `src/std/os.rs:1` has `pub mod fd;` ungated (`std::os::fd` does not exist on
  Windows); `src/tokio.rs:1` has `pub mod net` unconditionally importing
  `std::os::unix::net` and `tokio::net::UnixStream`; `src/std/net.rs:16-27`
  `UdpSocketExt::mtu` has only Linux and macOS arms; `src/socket2.rs:11-12`
  `SockAddrExt::new_unspec` uses the unix `sockaddr` layout. Core never calls
  `.mtu()`.
- `nix 0.29` and `libc` are unconditional in `adapter/ph` and `adapter/cli`.
  `nix` is unix-only.
- `aws-lc-rs 1.17` builds on Windows MSVC but needs CMake and NASM (or the
  `prebuilt-nasm` feature) on the runner. `capnpc` needs `capnp.exe`. The
  `[patch.crates-io]` capnp fork must build on Windows; nothing suggests it
  will not.
- Portable, no work: `libnode2`, `admin-api` (except the one `UnixStream`),
  the `zpr` common crate, `cbpf-rs`, `cslab`, `rcu`, `zpr-utils`, `snow`,
  `dalek`, `reqwest` (rustls), `ctrlc`, `rustyline`, `dirs`.

### 5. What is *not* platform-specific (checked)

No raw sockets, AF_PACKET, BPF devices or live pcap capture. No interface
enumeration, netlink, `getifaddrs` or MAC handling: `self_addr` comes from
config or from `connect()`-then-`local_addr()` (`main.rs:456-481`). Nothing
touches `/etc/resolv.conf` or system DNS. No daemonising, pid files or syslog.
No root or capability check in code; the TUN open simply fails without it.

### 6. Tests and CI

All integration tests are bash over `ip netns` and stay Linux-only.
`.github/workflows/adapter.yml` uses the reusable `rust-build-test.yml` /
`rust-test.yml` from `zl-zpr-dev-tools`, which take a `runs-on` JSON list and
fan out a matrix; adding `windows-latest` is a one-line input change plus
toolchain steps. Unix-only unit tests: `socket_access.rs`, `config.rs`
(mode assertions, `/tmp`), `main_argparse.rs` (`/tmp/*.sock`),
`batch_io.rs:1574-1617` and `assembly.rs:910` (`UnixDatagram::pair`).

## Decisions

**D1. Adapter only, elevated console, no service.** The first release is
`ph adapter` on an end-user PC run from an Administrator PowerShell. `ph node`
compiles on Windows (same binary) but is documented as unsupported and untested.
Service wrapper, installer and Event Log are deferred (see *Out of scope*).

**D2. Windows is a third arm of `sys/`, plus one new abstraction.** No unix
behaviour changes. The one abstraction is the wait set (D3). Everything else is
`sys/windows/` or a `#[cfg(windows)]` block next to the existing macOS ones.

**D3. The fastpath waits on a `WaitSet` of `Waitable`s, not on fds.**
Introduce a small `Waitable` trait and a `WaitSet` in `sys/`. Unix: a
`Waitable` is a `BorrowedFd`, `WaitSet::wait` is `poll(2)`; behaviour is
byte-identical to today. Windows: a `Waitable` is a HANDLE, `WaitSet::wait` is
`WaitForMultipleObjects`. The five sources map cleanly:

| Source | Unix | Windows |
|---|---|---|
| TUN | tun fd | `WintunGetReadWaitEvent` |
| substrate UDP socket | socket fd | Event bound with `WSAEventSelect(FD_READ)` |
| `Notify` ×3 | pipe read end | manual-reset Event (`CreateEvent`/`SetEvent`/`ResetEvent`) |

`fastpath_worker`, `fastpath_io`, `packet_queue` and `two_way_queue` are moved
onto `WaitSet` **first, as a unix-only refactor (C1)**, with existing tests
green and the netns tier green, so the Windows arm plugs into a proven seam.
Rejected: per-source reader threads plus channels (extra copy and hop per
packet, and a second datapath shape to maintain); a tokio async datapath on
Windows only (forks the datapath, loses `batch_io`).

**D4. Wintun via the `wintun` crate; addresses and routes via `netsh`.**
`sys/windows/zprtun.rs` wraps the `wintun` crate (0.5.x, safe bindings that
load the signed `wintun.dll` at runtime; the DLL ships next to `ph.exe`).
`PI_SIZE = 0`. `add_address`/`clear_address`/`has_address`/`add_route` shell out
to `netsh interface ipv6 add|delete|show address|route`, the same pattern as
`ip` and `ifconfig` today. `route_owner_conflict` parses
`netsh interface ipv6 show route` in a new `Platform::Windows` arm of the
existing route parser so its tests run on Linux. Upgrade path if `netsh`
parsing proves brittle or slow: IP Helper (`CreateUnicastIpAddressEntry`,
`CreateIpForwardEntry2`, `GetIpForwardTable2`) via `windows-sys`, which is
already in the lock file.

**D5. Windows batch_io is a `windows_unbatched` engine with no pktinfo.**
Socket side: non-blocking `recv_from`/`send_to` on `std::net::UdpSocket`. TUN
side: Wintun ring `ReceivePacket`/`AllocateSendPacket`/`SendPacket`. No
`WSARecvMsg`/`IP_PKTINFO`: an end-user adapter is single-homed for our
purposes and `self_addr` is configured or discovered once at start. The trait
signature change needed is `BorrowedFd` → the `Waitable` handle type from D3;
`libc::c_int` flags become a small `SendFlags` newtype. Ceiling stated in code:
multi-homed hosts and address-change-while-running are not handled on Windows.

**D6. Control RPC over a tokio named pipe with an explicit DACL.**
`\\.\pipe\zpr-control-<sid>` created with
`ServerOptions::create_with_security_attributes_raw` and a DACL granting
access to `BUILTIN\Administrators` and the owning user's SID only. The default
named-pipe DACL is not acceptable for a control channel. `ph-cli` connects with
`ClientOptions::open`. Cap'n Proto RPC runs over any `AsyncRead + AsyncWrite`,
so `admin_worker` and the ph-cli client change only in how the stream is
obtained. `socket_access.rs` and `prepare_socket_dirs` are `cfg(unix)`; their
Windows counterpart is the DACL above.

**D7. Capture is Unsupported on Windows in this release.** The capture pipe is
not created; `set-capture-file` returns `Unsupported` with a clear message. The
fd-passing design exists to keep `ph` from writing to user-chosen paths as
root, and there is no cheap equivalent on Windows (`DuplicateHandle` needs the
peer's process id and `PROCESS_DUP_HANDLE`). Deferred with an issue; the
`DuplicateHandle` design is the recommended follow-up. Passing a path was
rejected as a security regression.

**D8. The internal capture queue stops being an AF_UNIX socketpair.**
`packet_buffer_socket_pair` becomes the same in-house queue commit 726be13
introduced for the other worker queues, on every OS. It is in-process, so this
is a pure simplification with no Windows-specific code, and it removes the last
`UnixDatagram` from the datapath.

**D9. Paths and identity.** `%ProgramData%\zpr` replaces `/var/run/zpr` in
`admin-api` (`data_home.rs`, `socket_owner.rs`) behind `cfg(windows)`. Owner is
the current process token's user SID (both `ph` and `ph-cli` run elevated by
the same user in this release), not `SUDO_UID`. `geteuid` in `ph-cli` becomes a
`current_user_id() -> String` helper in `admin-api` with unix and Windows arms.

**D10. Signals.** `signal_worker.rs` gets a `cfg(windows)` arm on
`tokio::signal::windows`: `ctrl_c` and `ctrl_close` → graceful shutdown (second
`ctrl_c` hard-exits, as SIGINT does), `ctrl_break` → print counters (the SIGUSR1
role). `ctrl_shutdown` → graceful.

**D11. `zpr-ext` is fixed at the source and re-tagged.** Gate `std::os::fd`
and `tokio::net` on `cfg(unix)`, add a Windows arm to `mtu` (returns the same
hardcoded 1400 macOS uses, documented), gate `new_unspec` on `cfg(unix)`. No
API change on unix. New tag `zpr-ext-v0.6.0`; core bumps to it in C3.

**D12. Crypto stays on `aws-lc-rs`.** It supports Windows MSVC. The CI job
installs CMake and NASM (or enables `aws-lc-sys/prebuilt-nasm`). Switching to
`ring` for Windows was rejected: two crypto libraries in a security product is
worse than one build-toolchain step.

**D13. `ph-cli` builds without `pcap` on Windows.** The `pcap` default feature
is disabled for `cfg(windows)` in CI and documented; filter-string compilation
is unavailable there until Npcap is worth adding. `cbpf-rs` itself is portable.

**D14. Verification is a Windows CI job plus a hand-run smoke test.**
`windows-latest` builds `ph` and `ph-cli` and runs unit tests. End-to-end
traffic is verified by hand on a Windows VM against a Linux node and visa
service, with the script and result quoted on the umbrella. A Windows
integration tier is deferred.

### C1: fastpath waits on a `WaitSet` (`zl-zpr-core`, unix only)

**Blocked by:** none.

Add `sys/wait.rs`: `trait Waitable { fn handle(&self) -> WaitHandle<'_>; }`
and `struct WaitSet` with `wait(&mut self, timeout) -> Ready` where `Ready`
reports which entries are readable. Unix implementation: `WaitHandle` wraps
`BorrowedFd`, `wait` is the existing `nix::poll::poll` call moved verbatim.
`Notify` implements `Waitable`. Move `fastpath_worker.rs:66-80`,
`fastpath_io.rs:67-83`, `packet_queue.rs:268-270` and
`two_way_queue.rs:364-366` onto it. `BatchIoImpl` takes `WaitHandle`
instead of `BorrowedFd`; `libc::c_int` send flags become a `SendFlags`
newtype with `MSG_CONFIRM`/`MSG_DONTWAIT` constructors that are no-ops off
Linux. `posix_unbatched` and `io_uring` engines are adapted mechanically.

This task **changes no behaviour**. Every `poll` call it touches must produce
the same syscalls as before; if a review finds a behavioural change the task
is wrong.

**Tests.** Existing `fastpath_worker`, `packet_queue`, `two_way_queue`,
`batch_io` tests unchanged and green. One new unit test for `WaitSet` on unix:
two `Notify`s, post one, `wait` reports exactly that one ready.

**Acceptance.** `make check` clean on Linux and macOS. Netns tier green
(`zpr-dev build --test netns`), quoted in the PR. This touches the datapath,
so the gate escalation in `skills/zpr/SKILL.md` applies.

### C2: IPC and paths ready for a non-unix arm (`zl-zpr-core`)

**Blocked by:** none.

1. **Control stream abstraction.** `admin_worker` accepts any
   `AsyncRead + AsyncWrite + Unpin` for the RPC transport; the `UnixListener`
   accept loop moves into `sys/` as `control_listener()` (unix arm today).
   Same for the ph-cli client: `sys::control_connect()`.
2. **Capture queue** (D8): replace `packet_buffer_socket_pair` and the
   `UnixDatagram` sender/receiver in `queues.rs` and `capture_worker.rs` with

   queue's own full-signal replaces it. `assembly.rs:910` and
   `batch_io.rs:1574-1617` tests move off `UnixDatagram::pair` onto the queue
   or onto `UdpSocket` pairs on localhost.
3. **Capture Unsupported path.** The capture listener and
   `set_capture_file_worker` start only when `sys::capture_supported()` is
   true; otherwise `set-capture-file` RPC returns `Unsupported("capture is not
   available on this platform")`. Unix arm returns true, so nothing changes
   there.
4. **admin-api**: `current_user_id()` helper (D9); `socket_owner.rs` and
   `data_home.rs` gain a `cfg(windows)` arm (`%ProgramData%\zpr`, pipe name

   gets a named-pipe arm. `socket_access.rs`, `prepare_socket_dirs` and their
   tests become `cfg(unix)`.
5. `signal_worker.rs` gets the D10 Windows arm now, since it is independent
   of the datapath.

**Tests.** Existing admin_worker/ph-cli round-trip tests green. New:
capture-queue unit test replacing the socketpair test; `set-capture-file`

## Out of scope (deferred, each gets an issue at Z1)

- **Windows service and installer** (MSI/MSIX, start at boot, Event Log
  logging, `windows-service` crate). D1.
- **Capture to a file on Windows.** Recommended design: `ph-cli` opens the
  file and `ph` receives it via `DuplicateHandle`, preserving the "ph never
  opens a user-chosen path" property. D7.
- **`ph node` on Windows.** Compiles, unsupported, untested. D1.
- **Multi-homed hosts and address change while running** on Windows; needs
  `WSARecvMsg` with `IP_PKTINFO` in the Windows engine. D5.
- **Npcap** for `ph-cli` filter compilation on Windows. D13.
- **A Windows integration tier** (VM-based or two-runner). D14.
- **IP Helper instead of `netsh`** if parsing proves brittle. D4.
- **Non-elevated `ph-cli`** talking to an elevated `ph` (needs the DACL to
  admit a non-admin SID and the owner to come from somewhere other than the
  process token). D9.

## Open questions

1. **Wintun adapter persistence.** Wintun adapters can persist across runs by
   name and GUID. Should `ph` reuse an existing adapter named `tun_if` or
   always create fresh and delete on exit? Recommendation: create fresh,
   delete on graceful exit, and on startup delete any stale adapter with our
   name; decide in C3.
2. **`netsh` output locale.** `netsh` output is localised. The route parser
   fixtures are English; C3 should also try a non-English Windows locale or
   use `chcp`/`PowerShell -Command Get-NetRoute | ConvertTo-Json` if parsing
   localised text is unworkable. This is the main risk in D4 and the reason
   IP Helper is named as the upgrade path.
3. **Code signing.** `ph.exe` need not be signed to run from an elevated
   console; `wintun.dll` is signed by WireGuard LLC. Confirm nothing in the
   target environment (Defender SmartScreen policy) blocks an unsigned
   `ph.exe`. Not a code task; note the answer on the umbrella.
