**Goal.** `ph node` runs on a Mac (Apple Silicon or Intel), started by hand
with `sudo ph node -c x.toml` exactly as on Linux. It creates a utun
interface, addresses it, accepts docking adapters, forwards their traffic,
and reaches the visa service through its own TUN. The adapters and the visa
service stay on Linux. Behaviour is the same as on Linux; throughput is not.

**Not the goal** (see *Out of scope*): a launchd service, an automated macOS
integration tier, node-to-node links, node and adapter on the same Mac,
documenting the macOS adapter role.

## Background — what the node needs on macOS

The macOS adapter port put OS code in `sys/macos/` behind `ZprTun`/`TunCtl`
(`utun` via a `PF_SYSTEM` control socket; addresses by `/sbin/ifconfig`,
routes by `/sbin/route`), kept the POSIX pieces (`poll`, pipes, AF_UNIX,
`posix_unbatched` with pktinfo) and forced one worker. `ph node` is the same
binary, compiles and passes its unit tests on a Mac (the CI job that would
run them is inert, see §4), and has never been run.
Inventory taken by reading the code at the commits above; nothing was
executed. The node/adapter split itself is inventoried in the Windows plan
§1 and is not repeated.

All paths under `zl-zpr-core/adapter/ph/src/` unless shown in full.

### 1. The node's TUN is never addressed on macOS, on either path

`main.rs:289-304` computes `tun_addr`: the node's `zpr_addr[0]` when `tun_if`
is unset, `None` when it is set (a Linux-motivated rule — Linux cannot set an
IPv6 address at TUN creation — applied to every OS), and the comment says the
address is applied at creation.

It is not. `sys/macos/zprtun.rs:39-58` (`new_mq`) does
`tun::Tun::builder(addr.into())`: the `From<IpAddr> for IPV` impl
(`sys/macos/tun.rs:94-101`) reduces the address to its **family**, and the
builder's `with_address` (`tun.rs:360`) is `#[allow(dead_code)]` and never
called, so `configure` (`tun.rs:210-242`) skips `set_address`. The address is
only used to choose IPv4 vs IPv6 and to make `new_mq` fail with "address is
required on macos" (`zprtun.rs:49-51`, marked `// TODO: Temporary`) when it
is `None`.

So today a macOS node fails to start both ways:

- `tun_if` set → `new_mq` returns "address is required on macos" and
  `main.rs:313` panics "unable to create TUN device".
- `tun_if` unset → utun comes up unaddressed, `has_address` (ifconfig) is
  false, `local_zpr_addrs_missing_from_tun` (`assembly.rs:324`) is non-empty,
  and `main.rs:766` exits with the `ip -6 addr add` hint, which is the wrong
  command on macOS.

The macOS **adapter** works only because activation calls
`TunCtl::add_address` (`ifconfig <utun> inet6 <addr>/32 alias`,
`sys/macos/zprtun.rs:66-106`) and `add_route` for `fd5a:5052::/32`
(`link_state.rs:1603`, `:1661`). The node never calls either.

### 2. What the Windows plan's C1 already fixes here

C1 makes the node, before the startup check, call `add_address` for each
local ZPR address when `has_address` is false, then ensure the visa service
address is reachable via the TUN with `add_route`. On macOS both calls exist
and are already hardened (`add_route` handles "File exists" by inspecting
and replacing a stale route, `sys/macos/zprtun.rs:107-190`). After C1, the
`tun_if`-unset path works on macOS with no macOS code at all. The
`tun_if`-set path still dies in `new_mq` (§1), which is this plan's one code
task.

### 3. Already portable on macOS, no work

- **Substrate socket**: `set_recv_packet_info` and `set_reuse_port` are
  `cfg(unix)` (`main.rs:402-407`); `posix_unbatched` parses `IP_PKTINFO` /
  `IPV6_PKTINFO` (`batch_io.rs:1160-1190`). A macOS node can bind
  `0.0.0.0:5000` and sit multi-homed, the same shape as the Linux
  integration tests. No Windows-style concrete-`self_addr` rule, and no
  `WSAECONNRESET` analogue.
- **Everything in Windows plan §1 and §4**: forwarding, visa logic, VSS and
  VSConn, the AF_UNIX control socket, `tokio::signal::unix` signals,
  `set_carrier` NOP, one worker (`config.rs:94-101`; `new_mq` enforces it,
  `sys/macos/zprtun.rs:44-48`), packet steering degrading to a warning.
- **Capture**: the unix fd-passing path works on macOS as on Linux.

### 4. Tests, CI and docs

`.github/workflows/adapter.yml` would build `ph` and run its unit tests on
`macos-latest` (`:57`, `:113`), but **Actions is disabled on the forks**, so
nothing runs; the local gate (M5) is the only gate. Integration jobs are
`ubuntu-latest` only.
There is no hand-run macOS test document for either role, and
`zl-zpr-core/docs/SETUP.md` has **no macOS section** (`BUILD.md` mentions
macOS only as a build host). **No test anywhere runs a node on macOS.**

## Decisions

**M1. A dev/demo node, `sudo`, single worker, adapters and visa service on
Linux.** Apple Silicon and Intel, no OS floor beyond what the adapter already
needs. Wildcard and multi-homed binds are allowed (unix pktinfo), so the
Linux integration topology applies unchanged. Functional parity is the bar;
throughput of the single `posix_unbatched` worker is measured in C3m and
recorded, not fixed. No launchd service.

**M2. Nothing may assume `ph` is the only instance on the host.** Same text
as Windows N2: loopback dock listen must work, `tun_if` stays per-instance,
no new host-wide singleton. The uid-derived control path collision
(`config.rs:356`) is filed once, as
[zipline#169](https://github.com/mkolehmainen/zipline/issues/169); this plan
only inherits the constraint.

**M3. The node's self-address comes from the Windows plan's C1
([zipline#159](https://github.com/mkolehmainen/zipline/issues/159), merged as
[zl-zpr-core#61](https://github.com/mkolehmainen/zl-zpr-core/pull/61)); this
plan does not duplicate it.** C3m verifies on a Mac that C1's `add_address`
(`ifconfig alias`) and `add_route` make `fd5a:5052::1` reachable through the
utun. If C1 turns out to need a macOS-specific tweak (a /128 host route
rather than the /32, say), the fix lands under this plan's C3m and is
reported on [zipline#159](https://github.com/mkolehmainen/zipline/issues/159).

**M4. macOS `new_mq` stops requiring an address; the address picks nothing
but the family.** Remove the "address is required on macos" check and the
`TODO: Temporary`. `new_mq` builds the utun as IPv6 when `address` is
`None`, otherwise from the address's family as today, and never applies the
address (it never did). The misleading comment at `main.rs:285-290` is
rewritten: on every platform the TUN is created unaddressed and addressed
afterwards through `TunCtl`. The `ZPR_TEMP_LOCAL_ADDRESS` fallback at
`main.rs:299-303` is left alone (it is the adapter's and only picks a
family). The wrong-OS hint at `main.rs:758-761` becomes a per-platform
string from `sys/` (`ip -6 addr add` / `ifconfig ... inet6 ... alias` /
`netsh interface ipv6 add address`). Rejected: making `new_mq` apply the
address via the dead `with_address` builder (two ways to address a TUN,
and the startup check path would differ from Linux and Windows).

**M5. Verification is a hand-run test document plus unit tests; no new CI
tier.** `integration-test/macos-node-test.md` mirrors
`windows-node-test.md`: the Mac is the node, the Linux host runs valkey, the
visa service and its adapter, and a client adapter in netns; traffic flows
end to end. It is written against the merged `windows-node-test.md` so the
shared Linux-side steps are referenced, not copied. The things the code
reading could not settle are its checklist (C3m). Unit tests for M4 run on a
Mac through the core gate below. An automated macOS tier is out of scope (it would
need a macOS runner with root and a routable host; same shape as
[zipline#152](https://github.com/mkolehmainen/zipline/issues/152)).

**M6. Docs closure.** `SETUP.md` gains a "macOS" section covering **the node
role only** (what this plan verified); the adapter role on macOS stays
undocumented and gets a follow-up issue in Z1m. `docs/SYSTEM_OVERVIEW.md`
"Design decisions" records M1–M5 next to the Windows node decisions. This
plan is retired per `skills/zpr/SKILL.md`.

**Build gate used by every task below.** Same as the Windows plan: no root
`make check` in `zl-zpr-core`, no CI on the forks, so the **core gate** is
BUILD.md's CI equivalent run locally from the workspace root on the OS
named, transcript quoted in the PR:

```bash
cargo fmt --check
cargo build --all-targets --config 'build.rustflags = ["-D", "warnings"]'
make test
```

### C3m — [zipline#164](https://github.com/mkolehmainen/zipline/issues/164): `macos-node-test.md`, first end-to-end run, fixes it turns up (`zl-zpr-core`)

**Blocked by:** win-node C1, C1m.

Write `integration-test/macos-node-test.md` by inverting the Linux-side of
`windows-node-test.md` (or `windows-adapter-test.md` if the former has not
merged): the Mac runs `sudo ph node --self-addr 0.0.0.0:5000
--advertised-substrate-addr <Mac LAN IP>:5000 --tun-if utun9 --zpr-addr
fd5a:5052::2 ...`; the Linux host runs valkey, the visa service, the visa
service's adapter (`--node-addr <Mac LAN IP>:5000`) and `adapter1` in netns;
`adapter1` fetches from an HTTP server behind another adapter, exactly as
the adapter test does.

Run it once on a real Mac. Every item below is confirmed working or becomes
a fix in this task (small) or a filed issue (large), recorded in the
document's "Findings" section:

- After C1's `ifconfig ... inet6 <addr>/32 alias`, does the kernel install
  an on-link route for `fd5a:5052::/32` via the utun, or is C1's explicit
  `add_route` what makes `fd5a:5052::1` reachable? Record which, and whether
  `/32` or a `/128` host route is the right thing for a node (an adapter
  wants the /32; a node wants only the visa service on-link, since
  everything else is forwarded by the node itself).
- `tun_if` set (`utun9`) and unset (kernel-chosen `utunN`) both start.
- Wildcard `self_addr` with pktinfo: replies leave from the address the
  adapter docked to; try a second LAN interface if the Mac has one.
- macOS application firewall: whether `ph` prompts or is blocked for
  inbound UDP 5000 and TCP 8183, and the `socketfilterfw` command that
  fixes it.
- Two or more adapters docked at once through the one `posix_unbatched`
  worker; record observed drops/throughput as a number, do not tune.
- Shutdown: Ctrl-C removes the address and route (`teardown`), a second
  start does not fail on a stale route or a stale `utun9`.

**Tests.** The document is the test. Any code fix made here carries its own
unit test per repo convention.
